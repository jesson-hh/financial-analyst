# Telegram 只读会话通道：使用与运维

> 当前状态（2026-08-23）：自动化假 Telegram 端到端、无密钥本机界面检查和安全审查已经完成；真实 Telegram Bot 的实机正常路径尚未验收。本说明记录已经冻结的操作方式和安全边界，不是“真实 Bot 已验收”证明，也不应作为真实通道已经生产可用的承诺。

## 它能做什么

Telegram 是帷幄当前对话的只读出站消息界面，不是第二个控制台。

- 电脑端帷幄中成功发送的可见用户文字，以及 Agent 一轮结束后的最终回复，会按顺序镜像到唯一绑定的 Telegram 私聊。
- 用户明确要求后，Agent 可以把当前对话中已经生成并进入安全媒体仓的图片发送到 Telegram。
- 当前对话可以建立单次、每天、工作日或 A 股交易日定时任务；结果先写入帷幄历史，再按绑定关系发送。
- 一个帷幄对话最多绑定一个 Bot；一个 Bot 也只能绑定一个帷幄对话。

以下内容不会发送：Agent 思考过程、流式草稿、工具调用、运行进度、确认卡、内部错误、历史消息，以及未经明确发送或任务授权的普通图片和文件。

Telegram 入站消息不能向 Agent 提问、追加方向、打断任务、调用 Skill、审批操作或访问研究空间。未配对时，私聊仅用于识别接收者并签发临时配对码；配对后，从 Telegram 发来的文字、图片、按钮和命令会在通道边界被丢弃。

## 运维开启与关闭

该功能默认关闭。首期生产密钥保护依赖 Windows 当前用户的 DPAPI。

在观澜服务的运行环境中设置：

```text
GUANLAN_TELEGRAM_ENABLED=1
```

随后重启观澜服务。只有精确值 `1` 才会开启通道路由、Telegram 轮询、投递和定时任务；未设置、空值或 `0` 都保持关闭。关闭开关不会删除既有绑定数据，但通道不会轮询、投递或运行其定时任务，帷幄原有对话与研究功能继续工作。

这个环境开关只表示“开启功能”。Bot Token 绝不能写入 `.env`、`var/secrets.env` 或任何环境变量。

## 首次连接

连接由当前对话的 Agent 主导，但 Token 始终绕过模型。

1. 打开需要接收消息的帷幄对话，告诉 Agent：“连接 Telegram，Bot 名字叫……”。Bot 名字是观澜中的显示名称，由用户命名。
2. Agent 创建连接草稿后，对话中出现安全 Token 输入卡。只在这张卡中粘贴 Bot Token，然后提交。不要把 Token 作为普通对话发给 Agent。
3. 服务通过 Telegram 官方 Bot API 校验 Token，并显示校验后的 Bot 用户名；Agent 看不到、不能复述或导出原始 Token。
4. 在 Telegram 中私聊该 Bot，发送任意消息。Bot 会返回一个一小时内有效的临时配对码。
5. 回到创建草稿的同一个帷幄对话，把完整配对码告诉 Agent。配对码过期后重新私聊获取即可，不影响已经完成的其他绑定。
6. 电脑端会显示永久绑定确认卡。逐项核对 Bot、Telegram 用户名、数字用户 ID 和接收者，再确认。
7. 成功后，对话顶栏显示 `已连接 Telegram · <Bot名称>`。只从确认之后的新可见消息开始镜像，不补发此前历史。

“永久绑定”表示绑定跨服务重启保留，直到主动解除、凭证失效或 Bot 身份改变；它不表示 Token 永不过期。临时配对码始终只有一小时有效期。

若 Bot 已绑定另一个对话，或当前对话已有其他 Bot，系统会拒绝形成第二条绑定。先在原对话解除连接，再重新配对；不要用重复提交规避一对一限制。

## 从哪里查看与管理

绑定流程开始后，对话顶栏会出现 Telegram 状态标记；左侧对话列表只显示一个小状态点。点击顶栏标记或对话中的 Telegram 卡片，打开“Telegram 通道”管理抽屉。

抽屉只显示非秘密信息：Bot 和接收者、最近投递、队列数量、定时任务，以及安全的错误分类。界面永远没有“查看 Token”。

Telegram 入站提供的姓名、用户名不会进入 Agent 的工具结果，也不会作为模型上下文。配对时确需核对的自由文本只在电脑端本地确认界面显示；显示前会清除换行和控制字符，并整理成单行，避免它被当作指令或混入其他记录。

常见状态文案：

| 状态 | 含义与下一步 |
|---|---|
| `Telegram · 待配置` | 连接草稿已创建；在安全卡提交 Token。 |
| `Telegram · 等待配对` | Token 已校验；私聊 Bot 获取一小时配对码。 |
| `Telegram · 配对请求待确认` | 把完整配对码交给当前 Agent，并在电脑端核对永久绑定。 |
| `已连接 Telegram · <Bot名称>` | 绑定有效；批准后的新文字可以正常镜像。 |
| `Telegram · 重试中` | 暂时性失败正在按顺序自动恢复，不要重复发送。 |
| `Telegram · 投递待确认` | Telegram 可能已收到，但本机没有可靠回执；需要人工处理。 |
| `Telegram · 需要重新连接` | Token、Bot 身份、接收者或轮询状态需要处理；按抽屉提示替换 Token、重新校验或重新配对。 |
| `Telegram · 已暂停` | 新消息不会进入投递队列，恢复前也不会补发暂停期间的历史。 |

## 文字、图片和定时任务

### 文字

绑定生效后，电脑端普通用户消息和 Agent 最终回复自动镜像。长文字由系统安全拆分并保持顺序。Telegram 故障不会阻止帷幄先保存消息或让 Agent 继续工作。

### 图片

先让 Agent 在当前对话中完成计算并生成图片，再明确说“把这张图发到 Telegram”。发送确认卡会显示图片、说明和唯一目标；确认只授权这一次投递。

任意本地路径、网络 URL、其他会话的图片，或尚未进入安全媒体仓的文件都不能直接发送。普通生成图片不会因为 Bot 已绑定而自动外发。

### 定时任务

可以对当前对话说，例如：

- “每天香港时间 08:15 生成盘前晨报，并同步 Telegram。”
- “每个 A 股交易日收盘后复盘；只发送文字。”
- “暂停晨报。”

创建或修改时，在电脑端确认任务名称、完整内容、单次/每天/工作日/A 股交易日、时间、时区以及是否允许附图。`A 股交易日` 使用真实交易日历；日历不可用时任务会阻塞，不会用普通周一至周五冒充。

任务到点后先在同一个帷幄对话运行，最终可见结果才会镜像。对话正在忙时，任务排队等待，不打断正在进行的 Agent。服务恢复时，每个任务最多考虑最近一次漏跑；默认超过六小时不再补跑，避免集中发送过期晨报。附图必须在已经确认的任务中明确允许，并且只能发送该轮新生成、已校验的图片。

## 暂停、恢复、替换与解除

### 暂停镜像

在通道抽屉选择“暂停镜像”，或直接告诉当前 Agent 暂停 Telegram。尚未开始发送的待发/重试项会取消；恰好正在发送而无法确认结果的项目会进入“投递待确认”。暂停后产生的对话不会排队等待未来补发。

归档对话或归档其研究空间时，绑定和定时任务也会先安全暂停。恢复对话只恢复帷幄可见性，Telegram 和定时任务仍保持暂停，必须由用户显式恢复。

### 恢复镜像

在恢复后的普通对话中选择“恢复镜像”，或让 Agent 恢复。系统从恢复时的最新对话位置继续，只发送此后的新内容；暂停期间的历史不会补发。凭证失效、Bot 身份变化或轮询冲突属于故障暂停，必须先按提示修复，不能用普通“恢复”强行越过。

### 重新校验与替换 Token

“重新校验 Bot”用于核对当前 Token 对应的 Bot 身份。“替换 Token”只会打开新的安全输入卡，仍不能把 Token 交给 Agent 或放入普通消息。

新 Token 如果仍属于同一个 Bot，可在校验后恢复原绑定；如果 Bot 数字身份改变，系统不会沿用原接收者，必须重新走私聊配对和电脑端永久绑定确认。

### 解除连接

解除连接需要电脑端确认。解除后，尚未发送的内容会取消，新消息停止镜像，但帷幄对话历史不会删除。以后重新连接从新的确认点开始，绝不补发旧消息。

### 归档与硬删除

只要这个对话曾经产生过 Telegram 通道历史，当前版本就会安全阻止对它执行硬删除。请保留该对话，或使用归档与还原管理它；解除连接并不会解除这项保护。

这样可以避免帷幄对话已经删除，而 Bot、接收者、投递记录或定时任务仍留在通道记录中。未来只有在提供一套明确、可核对、同时清除整条关联记录的流程后，才允许真正删除这类对话；在此之前不要通过手工改库或删文件绕过保护。

## 投递异常怎么处理

通道抽屉中的投递状态以服务端真实记录为准，不要根据按钮点击后的瞬间变化猜测已发送。

### `retry_wait` / “重试中”

这是明确可以恢复的暂时性问题，例如短暂断网、服务错误或 Telegram 限流。系统保留顺序并自动退避重试。保持服务运行并等待，不要在帷幄中重复发同一内容，否则恢复后可能出现业务上的重复消息。

### `uncertain` / “结果待确认”

请求可能已经到达 Telegram，但成功回执在途中丢失。为防止重复发送，系统停止盲目重试，并阻塞该绑定后续顺序。

先打开 Telegram 检查该条是否已经出现，再在抽屉选择：

- 已出现：选择“视为已送达并继续”。
- 未出现且可以接受重复风险：选择“重新发送并接受可能重复”。
- 不再需要：选择“放弃本条并继续”。

系统不会替用户自动选择，也不承诺网络故障下严格的“只发送一次”。

### `terminal` / “已停止”

这是明确不能继续自动重试的失败，例如 Token 失效、用户屏蔽 Bot、目标不可达或图片校验失败。先修复原因，例如替换 Token、重新校验 Bot、解除 Telegram 端屏蔽或重新生成合规图片；随后选择“修复后重试”。如果内容已经过期，选择“放弃本条并继续”。

身份变化、凭证不可用或同一 Bot 被另一程序轮询时，连接会保持可见但暂停，不会删除绑定或改接其他接收者。

## 备份、恢复与 Windows 账户迁移

通道状态默认位于：

- `var/console/channels.sqlite3`：Bot/绑定的非秘密元数据、投递队列、游标和定时任务。
- `var/console/channels.sqlite3.history-present`：不含秘密的历史存在标记；数据库暂时缺失时，它负责阻止系统误建空库或误删仍有关联的对话。
- `var/console/channel_secrets/`：由 Windows 当前用户 DPAPI 加密的 Token 密文。

三者必须作为同一个时间点的备份保管。数据库虽不含原始 Token，但包含 Telegram 接收者标识、投递状态和任务配置，仍应视为敏感业务数据。历史存在标记不能单独删除；标记存在而数据库缺失时，系统会按部分恢复故障安全停用相关迁移、投递和生命周期操作，不会自动创建空库继续运行。

推荐备份步骤：

1. 正常停止观澜服务，确认通道后台任务已经退出。
2. 同时复制 `channels.sqlite3`、`channels.sqlite3.history-present` 和整个 `channel_secrets/` 目录；不要只复制其中一部分。SQLite 使用 WAL，服务运行中不能简单只复制主数据库文件；确需在线备份时应使用 SQLite 在线备份机制，并把历史存在标记纳入同一恢复点。
3. 如需恢复完整帷幄上下文，同时备份 `var/console/sessions/`；通道备份本身不等同于对话历史备份。
4. 在受控位置保存备份，不上传公开网盘、代码仓库或工单附件。

恢复到原 Windows 用户时，也必须保留该用户配置中的 DPAPI 主密钥。仅复制密文文件不能重建 DPAPI 能力。

DPAPI 的 CurrentUser 保护不是可移植的 Token 导出格式。换电脑、换 Windows 登录账户、丢失原用户配置或 DPAPI 主密钥后，即使数据库和密文文件都在，新服务也可能显示 `credential_unavailable`。这是预期的安全失败：不要尝试把密文降级成明文或写进环境变量；在新账户中通过“替换 Token”的安全卡逐个重新提交，并按界面要求重新校验或重新配对。

## 安全红线

- Token 只能粘贴到帷幄安全 Token 输入卡。
- 严禁把 Token 放进普通对话、转向消息、Agent Prompt、定时任务 Prompt、Skill、环境变量、配置文件、命令行、脚本、日志、工单、测试 fixture 或 Git 提交。
- Token 仍在输入框时，严禁截图、录屏、DOM/页面快照、浏览器开发者工具采集或日志导出。提交并确认输入框已清空后，才能进行界面验收。
- 不要让 Agent 复述、导出、保存或“记住”Token；Agent 的正确行为是要求使用安全卡。
- 不要把 Telegram 数字用户 ID 当作 Token，也不要用手工修改数据库把它改成任意接收者。
- 配对码只交给创建草稿的当前 Agent，并在一小时内使用；最终接收者仍以电脑端确认卡为准。
- 不把 `channel_secrets/` 密文当作无敏感信息的普通附件。它不能直接显示 Token，但仍应按凭证备份保护。

## 发布与真实 Bot 验收闸

真实 Bot 验收必须在假 Telegram 端到端、安全泄漏扫描和无秘密界面检查通过后进行。真实 Token 只能由用户粘到安全卡，不能出现在实施聊天、终端、测试代码或截图中。

最低实机路径包括：校验真实 Bot 用户名、私聊取码、电脑端确认一对一绑定、确认标题状态、发送用户文字与 Agent 最终回复、显式发送一张测试图、确认 Telegram 普通入站对 Agent 零反应，以及服务重启后绑定仍在。

截至本文状态日期，上述真实 Bot 路径尚未执行，因此不能标记为“已实施并实机验收”。
